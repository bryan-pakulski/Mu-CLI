Context growth

Shows: top — the harness's cl100k_base estimate (dashed) vs the provider's real prompt size (solid) per iteration, with the context limit and compaction events marked. Bottom — a heat strip of which context layer (L0–L5) dominates each iteration, plus a diverging drift strip.

Why: suspect #1 lives here. If the estimate diverges from actual, the compaction budget (computed in cl100k tokens) fires at the wrong point. The heat strip shows which layer is eating the budget — usually L5 history ballooning.

Read: dashed above solid = the harness over-estimates (compaction fires too early). Solid above dashed = under-estimate (fires too late, may blow the window). Blue verticals = compaction. If the limit line is off-chart, its value is printed top-right.

Tokenizer drift (actual − est) / actual · 100 — the headline diagnostic
Tokenizer drift

Shows: per-iteration drift between the real prompt size and the harness estimate, centered at 0%. The ±15% band is shaded — inside it the estimate is "good enough".

Why: this single chart decides suspect #1. Persistent drift outside the band means the compaction budget is systematically wrong for this model's tokenizer.

Caveat: the formula normalizes by the real prompt, so when that is small early in a turn the percentage can spike to ±2000% and the mean becomes meaningless (use median). The y-axis is clamped to keep the warn band visible; ▲▼ caps mark values beyond the clamp. Toggle signed-log to read the full range. Absolute drift is visible in Context growth.

Read-state / redundant reads

Shows: a path × iteration grid of read-tool calls (read_file, get_chunk, list_dir, search_…). Red cells are redundant — the same path was read again with no write in between.

Why: quantifies the context-gathering stall the recoverage nudge reacts to, and separates re-reading caused by state loss (clusters after a compaction) from aimless re-reading.

Memory & scratchpad counts

Shows: task-memory and scratchpad entry counts per iteration (lines), with a faint stacked area of the task-memory status mix (active / pending / stale / done / pruned) behind them.

Why: the counts show how much memory the model is carrying; the status mix shows whether it's going stale — a growing stale/pruned share with no done entries means memory is accumulating without resolution.
